## Optimizations applied, in order

1. **`repartition(8)` after binaryFile read** — the small-file problem solved
   at the source. 5,000 partitions of 1 file each → 8 partitions of ~625 files
   each. Each task now does real work instead of paying task-launch overhead.

2. **`.cache()` on parsed DataFrame** — Spark recomputes by default. The parse
   step ran twice in baseline (once for count, once for write). Caching is a
   memory tradeoff: ~MB held in RAM per cached partition vs N seconds of CPU.

3. **`coalesce(4)` before write** — produces 4 output files instead of 8.
   `coalesce` is shuffle-free (cheap) but only reduces partition count.
   `repartition` would also work but adds shuffle cost.

4. **AQE skew detection + advisory partition size** — lets Spark adjust
   partition counts at runtime based on actual data sizes. Free wins on
   skewed joins, which our `field_lineage` extraction is prone to.

## Optimizations NOT yet applied

These would matter more at higher scale and we'd add them when we cross those
thresholds:

- **Broadcast joins** for small-DataFrame joins (would benefit Day 5's
  catalog-to-lineage join when one side is < 200MB)
- **Predicate pushdown** for partitioned Parquet reads (matters when
  reading 100s of GBs filtered by business_domain)
- **Bucketing on table_name** for repeated joins (matters when downstream
  always joins on table_name)
- **Pandas UDFs / Arrow** to reduce Python serialization overhead (worth it
  when UDFs become a major share of total time)

## How this would change at 100x scale

At 500,000 YAMLs (~5GB raw):
- Local Spark would be CPU-bound; need a real cluster
- Partition strategy: 200-400 partitions, ~25MB each
- Output: 50-100 Parquet files at 128MB each (BigQuery's sweet spot)
- Pandas UDFs become essential — Python serialization dominates
- We'd partition the lineage Parquets by upstream_namespace for query-time
  predicate pushdown

## How this would change at 1000x scale (real warehouse)

At 5M+ YAMLs (50GB+ raw):
- Spark Operator on GKE with 20+ executors
- Adaptive executor allocation
- Output to GCS, not local disk
- Read via partitioned source, not file glob
- Probably switch from binaryFile to a proper schema-aware reader
- Lineage extraction becomes its own scheduled job, not part of ingestion
